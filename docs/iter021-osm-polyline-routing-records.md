# Iter021 — OSM road geometry → SDAL Cartographic polylines and Routing segments

## Production objective

The user wants **a complete, reliable OSM PBF → SDAL 1.7 → ISO encoder**, not an unrelated decoder. This iteration adds genuine source-to-wire line/road record codecs plus a bounded *OSM-normalized road → two SDAL record types* producer. The existing one-command \`build.sh\` remains canonical; the fully tested hybrid ISO writer is unchanged. **Do not cut over \`main.py\` to a half-populated map** until physical block placement, routing conditions, typed data, catalog authority and all backreferences validate.

Primary authority: uploaded *PSF Specification for SDAL Format 1.7*, version 0.4, specifically **§3.5.3.3** (Cartographic Full Polyline), **§3.5.3.4** (Short Format), **§3.5.6.3** (Cartographic Position), **§3.3.4.1** (left/right segment orientation) and **§3.3.4.3** (Route Calculation Segment Record). Variable integer and N+1 record-block encoding was introduced in Iter020.

## Direct original evidence, not only an artificial example

The following source was independently inspected by reading the unmodified original **WE_06Q4 BENELUX1.SDL**, 350,914,560 bytes, at physical Parcel ID **0x00092D7A** (position **0x092D7A00**), a genuine uncompressed Cartographic type-1 parcel with a 184-byte fixed typed header.

- The original \`lineDesc\` decodes as \`usOffset=768\`, \`usCount=7\`, \`ucBlkCnt=1\`, \`ucRecsPerBlk=4\` (2^4 record capacity), \`usMaxSize=15\`, \`usDataOffset=676\`, \`usMaxBlkSize=92\`.
- At actual relative byte **676** the block begins with an eight-byte length table: one first-record offset and **seven per-record lengths**.
- The seven original record lengths are **10, 10, 13, 13, 10, 13, 15** bytes. These were independently extracted using the actual block length table, and **all seven records decoded successfully** under the §3.5.3.3 Full Format grammar, including geographic Type4 deltas and the presence/absence of navigation-specific fields.
- The original spatial bounding rectangle and scale field were read separately; the trial decoded real source records rather than comparing only encoder-generated bytes.
- This is a **strong, limited** proof for seven authentic uncompressed Full Polyline records from one regional map. It is not proof of all Cartographic record variants, and no proprietary binary parcel or record bytes are included in this repository.

The newly published \`tools/oem_line_segment_evidence.py\` is provided to repeat that check across sampled Cartographic and Routing physical Parcel IDs from the Iter018 descriptor reports. The previously measured original seven-record result was an **independent direct-original scan**, not an execution record of that exact newly published tool. It remains an explicit release-acceptance item to replay the new script against both complete originals. CI uses **synthetic/generated data**, deliberately not copyrighted OEM binaries.

## New actual production encoders

### \`src/sdal_builder/oem_line_geometry.py\`

1. **Full Cartographic Polyline (§3.5.3.3):** 15-bit Position Offset with high record-format bit zero; Text Record Count; Type1 entity type; Type4 latitude/longitude relative to minimum bounding coordinates at the true parcel scale; navigation/direction/route-type flags; if navigable, rank/divider/multi-digitized and normalized attribute index; Type1 Position Count; declared two-byte text offsets. Required fields are never defaulted after decoding, reserved bits are rejected and the inverse reproduces exact bytes.
2. **Position (§3.5.6.3):** three-byte record containing internal-point flag, pen-toggle flag, **signed 11-bit latitude and longitude deltas** (two's complement, each -1024..1023), calculated from the previous vertex. Whole-array operations preserve the full ordered polyline, and refuse any nonexact scale conversion or out-of-range delta. No points are silently dropped, truncated or moved.
3. **Short Polyline (§3.5.3.4):** a deliberately restricted **two-point patch** with 7-bit first deltas, reference to a concrete full polyline index and Type4 start position. Additional short delta records (Next Point Flag=1) are not fabricated or ignored: unsupported forms fail closed. The spec's first delta orientation (start minus following point) is preserved; the bounded codec only accepts representable positive deltas in this form.

### \`src/sdal_builder/oem_route_segments.py\`

Encodes and decodes the **regular, bottom-layer Segment Record** of §3.3.4.3. The supported profile includes:

- Explicit travel direction 1/2/3, 8-bit left/right bearings, rank, divider flags, detailed city flag and cartographic highlighting layer.
- Type1 references to **actual local routing-node indexes**, plus Type1 travel cost in seconds, real segment length in meters and normalized attribute index.
- Encodes mandatory flag bytes; it refuses aggregation, POI/sign flags, supernode endpoints, conditions, shape-point flags, time-zone/long-haul/driving-side supplements, NavID and other optional structures, rather than silently dropping them.
- \`verify_routing_node_segment_links()\` establishes that each segment is referenced by its two actual endpoint Routing Node records and that every node's incident-segment index set agrees exactly with the segment array. A globally valid geographic path is a separate requirement.

### \`src/sdal_builder/osm_road_encoding.py\`

\`encode_osm_road_records()\` accepts **normalized, already clipped** OSM road vertices in integer NTUs, real routing-node indexes, declared travel permission, explicit bearings, segment length, travel cost, rank/road category, attribute-index authority and the **actual allocated Cartographic Position Offset**. It produces three independent but related output wire structures:

- Full Cartographic Polyline record (type 1)
- Complete array of signed Cartographic Position records for all subsequent vertices (type 1)
- Regular bottom-layer Routing Segment record (type 0)

The encoder respects the **canonical left/right node orientation** in §3.3.4.1 (smaller longitude, then smaller latitude). When input OSM vertex order runs the other way, it reverses all vertices, swaps local node endpoints and also swaps one-way permission 1 ↔ 2. If both endpoints have equal coordinates, it requires explicit Z-level authority and fails rather than inventing an ordering.

All vertices must fit the declared physical spatial parcel and be representable without loss. Inadequately clipped roads, mismatched OSM endpoint coordinates, a missing travel permission, invalid node IDs, out-of-range travel cost, impossible scale and missing attribute authority are errors.

**Deliberately not guessed:** OSM highway priority → SDAL rank, maximum-speed policy → route travel cost, normalized attribute dictionary indexes, geographic segment clipping, Z-level and interparcel ghost nodes. These are caller-provided or separate required production stages. Generating arbitrary values for them would create a navigationally misleading disc.

## Corruption-resistance and tests

- \`tests/test_oem_line_geometry.py\`: complete Full Polyline control records, direction/flag parity, signed-delta edge values, pen flags, full-vertex reconstruction, representability failures and intentionally bounded Short Polyline variants.
- \`tests/test_oem_route_segments.py\`: bit-exact regular segment record, composition with the existing variable record-block serializer, reciprocal node/segment references, unsupported optional flags and invalid link/cost/length cases.
- \`tests/test_oem_osm_road_encoding.py\`: reversed OSM one-way input → correctly reoriented SDAL one-way semantics, all original geometry vertices preserved, segment cost/length retained and malformed geometries/endpoint IDs refused.
- \`tests/test_oem_line_segment_evidence.py\`: physically placed synthetic type-1/type-0 parcels with actual fixed typed headers, BlkDesc arrays, record block offsets, variable length tables and actual generated line/segment records, then read by the very same released OEM evidence tool; byte corruption is detected.
- The full cumulative GitHub CI suite still includes real ISO9660/Joliet/UDF mastering on Linux and macOS, with payload SHA-256 parity.

## Exact acceptance boundary and next work

Iter021 **does not** claim that complete Cartographic or Route Calculation parcels have been generated from an arbitrary OSM PBF, or that a valid Denso disc is already producible. It provides authentic format record encoders and a functional normalized-OSM-to-record conversion, **but cannot replace \`main.py\` without more real format coverage**.

Remaining production-critical components in dependency order:

1. Source-accurate clipped OSM segment graph including shared boundary nodes, ghost nodes and original way identities.
2. Position/Polyline/Segment **physical record array placement**, full BlkDesc offsets and Parcel Size Index table authority; enforce the fixed spatial header and all actual local/out-of-region references.
3. Additional navigable features: multipoint Short Polylines, Route Segment shape records, turn conditions, restrictions, supernodes, attributes, text/navigation indexes and crossreferences.
4. Evidence-backed **SZIP compressor/decompressor** for OEM-compatible payloads or a separately proved valid uncompressed complete-parcel profile.
5. Assembly with Iter017–019 Global KD and metadata, strict generated end-to-end reference audit, existing hybrid ISO mastering and **Denso hardware loading/display/route tests**.

This iteration keeps the single-source project architecture and does not add TODOs, migration compatibility, phantom data or duplicate build paths.
